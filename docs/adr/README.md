# 架构决定记录（ADR）

这里放**撤销成本较高**的决定：分层方式、数据格式、约束的松紧、横切机制（日志/配置/出网/持久化）的归属。

## 什么时候必须写一条

满足任意一条就该写：

- 改动会跨越模块边界（新增一层、改变依赖方向）
- 改数据格式或对外接口，需要迁移
- **放宽**任何一条 `docs/architecture.md` 里的否命题
- 引入新的外部依赖、网络出口或凭据存储方式
- 同一件事有两种以上实现，你要选一种留、一种删

反过来，纯粹的代码整理、加测试、修 bug、加一条新规则**不需要** ADR——那些用 issue 就够了。

## 格式

文件名：`NNNN-简短标题.md`（四位序号，递增）。

```markdown
# NNNN. 决定的一句话总结

- 状态：提议 / 已采纳 / 已废弃（被 NNNN 取代）
- 日期：YYYY-MM-DD
- 关联：issue #N、否命题 A<N>

## 背景
现在是什么样，为什么需要动。

## 决定
一句话说清做了什么选择。

## 为什么不是别的选项
逐个说清被否掉的方案和否掉的理由——**这是 ADR 最有价值的部分**，
因为下一个 agent 最容易犯的错就是把否掉的方案重新提一遍。

## 后果
- 变好的地方
- 变差的地方 / 接受的代价
- 解冻条件（如果有存量债务被冻结）

## 怎么验证这条决定还活着
它对应哪个 metric / 哪条规则 / 哪个测试。
```
